# FastProof reporter protocol

This is the contract that `@franshub/fastproof-playwright` and `pytest-fastproof` implement. A reporter for
another framework that follows it behaves the same way: live results and logs, correct attempts, attachments
deduplicated by hash, trace correlation, masking at the source, and an offline spool that never fails the
test run.

All paths are relative to the server URL (`FASTPROOF_URL`, for example `https://fastproof.example.com`).
Every request carries `Authorization: Bearer <FASTPROOF_TOKEN>`; the token needs `launches:write` in the
project (role `uploader`). JSON is camelCase. Errors have the body `{code, message, details?}`.

## 1. Configuration

| Variable | Meaning |
|---|---|
| `FASTPROOF_URL` | server URL; without it the reporter is off (one notice, the run is unaffected) |
| `FASTPROOF_TOKEN` or `FASTPROOF_TOKEN_FILE` | API token (never written to the spool) |
| `FASTPROOF_PROJECT` | project key, `^[a-z0-9][a-z0-9-]{1,62}$` |
| `FASTPROOF_LAUNCH` | launch external id; every process with the same id joins one launch (default: from CI, see 2) |
| `FASTPROOF_LAUNCH_NAME`, `FASTPROOF_ENVIRONMENT` | launch name, environment key (part of test identity) |
| `FASTPROOF_ENABLED=false` | turn the reporter off without touching the test config |
| `FASTPROOF_OFFLINE=true` | write only the spool |
| `FASTPROOF_SPOOL_DIR`, `FASTPROOF_SPOOL_MAX_BYTES` | spool directory (default `.fastproof/spool`) and size limit (default 200 MB) |
| `FASTPROOF_FLUSH_TIMEOUT_MS` | how long the end of the run waits for uploads (default 30000) |
| `FASTPROOF_LIVE_LOGS=false` | do not stream logs |
| `FASTPROOF_SECRET_ENV`, `FASTPROOF_SECRET_PATTERNS` | comma lists: extra env names/globs whose values are masked, extra regular expressions |
| `FASTPROOF_TESTPLAN` (or `ALLURE_TESTPLAN_PATH`) | Allure-format `testplan.json` |
| `FASTPROOF_QUIET=true` | only warnings |
| `FASTPROOF_DIRECT_UPLOAD_MODE=off`, `FASTPROOF_DIRECT_UPLOAD_MIN_BYTES` | no direct uploads to S3; smallest attachment sent directly (default 1 MiB), see 5a |

Options in the runner's configuration override the environment, except `FASTPROOF_ENABLED=false`, which
always wins.

## 2. Launch

```
POST /api/v1/projects/{key}/launches
Content-Type: application/json

{"externalId": "gitlab-42-1001", "name": "group/app #7",
 "attributes": [{"key": "suite", "value": "e2e"}],
 "ci": {"provider": "gitlab", "pipelineId": "1001", "jobId": "555", "url": "...", "buildOrder": 7},
 "vcs": {"repository": "...", "branch": "main", "commit": "..."},
 "environment": {"key": "staging", "values": {}}}
```

`201` creates the launch, `200` returns the existing one with the same `externalId`. The reporter always sends
an external id, so the call is idempotent:

- explicit `FASTPROOF_LAUNCH` or option;
- else CI: GitLab `gitlab-<CI_PROJECT_ID>-<CI_PIPELINE_ID>`, GitHub
  `github-<GITHUB_REPOSITORY>-<GITHUB_RUN_ID>-<GITHUB_RUN_ATTEMPT>`, Jenkins `jenkins-<JOB_NAME>-<BUILD_NUMBER>`
  (the same rules as the `fastproof` CLI, so shards, the CLI and reporters join one launch);
- else `local-<uuid>` generated by the run ("own launch").

The launch is started in the background when the run begins; hooks never wait for it.

**Finish.** `POST .../launches/{id}/finish {"status": "finished"|"interrupted"}`. With `finishLaunch: auto`
(default) only an own launch is finished, because shards that share an external id cannot know which one is
last; CI pipelines finish shared launches with `fastproof launch finish` in a final job. `always` and `never`
override it.

## 3. Results

```
POST /api/v1/projects/{key}/launches/{id}/results
Content-Type: application/x-ndjson

{"id": "py-3f2a9c1b7d4e-5b1c...-0", "name": "test_pay", "status": "running", "start": 1763712000000, "retry": 0}
{"id": "py-3f2a9c1b7d4e-5b1c...-0", "name": "test_pay", "status": "failed", ...}
```

Response `202 {accepted, duplicates, rejected: [{index, message}]}`. Each line is a `ReportResult`
(`schemas/fastproof-report-v1.json`), **one attempt** of one test.

- **Client id** (`id`): unique per attempt and per run, stable across HTTP retries and spool flushes:
  `pw-<runId>-<playwright test id>-<retry>`, `py-<runId>-<sha1(nodeid)[:16]>-<attempt>`; the Allure enhancers use `aj-<runId>-<allure result uuid>` (JavaScript), `jv-…` (Java) and `ap-<runId>-<sha1(nodeid)[:16]>-<attempt>` (Python); `runId` is 12 random
  hex characters per run. Sending the same id again is a no-op (`duplicates`), so every retry is safe. A
  random run id keeps a re-run CI job (same external id) from being dropped as duplicates.
- **Attempts**: every attempt is its own result with the same identity (`fullName`, `testCaseId`, parameters)
  and `retry` = zero-based attempt number; the server groups them, the latest start wins, and mixed outcomes
  mark the result flaky. Playwright: `result.retry`. pytest: each `pytest_runtest_logstart` /
  `pytest_runtest_logfinish` pair is one attempt, which covers pytest-rerunfailures (it calls them per rerun).
- **Running results**: when a test begins, the reporter sends the same client id with `status: "running"`
  and the fields known at that point; the final result later updates it. Send the identity the final line
  will have (`fullName`, `parameters`, `testCaseId`) whenever it is known at the start, so the running row is
  the right one from the first moment. The client id wins: when the final line carries another identity (an
  added `testCaseId` or `parameters`, another `fullName` or `name`), the server moves the attempt to the
  result of the final identity, recomputes both results and removes the running result when it has no
  attempts left. Several running lines of different tests never merge their outcomes.
- **Counts**: `accepted` counts lines applied, a running line completed by its final line in the same
  request included; `duplicates` counts lines whose client id is already stored as a final result. Feature detection: if the server
  rejects a running line (stage B answers `rejected` with "unknown variant `running`"), the reporter stops
  sending them; final results are unaffected. Running lines are never spooled.
- **Final result**: `status` (`passed|failed|broken|skipped|unknown`), `start`/`stop` (ms since epoch; always
  send `stop`, otherwise the server treats the attempt as interrupted), `durationMs`, `error {message, trace}`,
  `steps` tree, `stdout`/`stderr`, `labels` (`framework`, `suite`/`subSuite`/`parentSuite`, `tag`,
  `thread`, annotations or markers), `links`, `parameters`, `testCaseId` (explicit id annotations/markers),
  `source {file, line}`, `traceparent`, `attachments [{id, name, contentType}]`.
- **Batching**: one sender per process, every 200 ms or at 500 lines; at most 500 results or 4 MB per request.
  Results are posted in order by a single in-flight request, so a running line always precedes its final line.
  `413` with several lines: resend them one by one; `413` with one line: drop it and warn.

## 4. Live logs

```
POST /api/v1/projects/{key}/launches/{id}/logs
Content-Type: application/x-ndjson

{"resultId": "<client id>", "attempt": 0, "seq": 0, "ts": 1763712000123, "level": "info", "stream": "stdout", "message": "..."}
{"resultId": "<client id>", "attempt": 0, "seq": 1, "ts": 1763712000125, "level": "info", "stream": "step", "message": "▶ pay", "step": "checkout › pay"}
```

- `resultId` is the attempt's client id, `attempt` its number, `seq` increases from 0 per `(resultId, attempt)`
  (the idempotency key), `ts` is milliseconds since the epoch (an RFC 3339 string is accepted too; the server
  returns milliseconds), `level` is `trace|debug|info|warn|error` (the server also reads `warning` as `warn`
  and `fatal`/`critical` as `error`, and rejects other values), `stream` is `stdout|stderr|log|step`, `step`
  is the step path joined with ` › `.
- Server limits (defaults): 5000 lines and 8 MiB per request, 64 KiB per message, 256 MiB of log bytes per
  launch. The server cuts a longer message at a character boundary and ends it with ` …[truncated]`; the line
  is kept. A request over a limit gets `413` naming the limit and its unit. The reporters cut messages to 64 KiB
  themselves, send at most 1000 lines per request and queue at most 20000 lines; the oldest are dropped first
  when the server is slow.
- Sources: Playwright `onStdOut`/`onStdErr` and `onStepBegin`/`onStepEnd` of `test.step` (plus failed
  `expect`); pytest a `logging.Handler` on the root logger (level `fastproof_log_level` or
  `FASTPROOF_LOG_LEVEL`, default INFO; pytest's own `log_level`, when set, also limits what reaches it) and
  `pytest_fastproof.step()`. Captured stdout of pytest arrives per phase in the final result, not live.
- **Feature detection**: `404`, `405` or `501` mean the server has no logs endpoint; the reporter stops
  streaming. pytest also probes with an empty request after the launch resolves. When logs are not stored live,
  the buffered log records (bounded, 1 MiB per attempt) are appended to the final result's `stdout` after a
  `--- log ---` line, so nothing is lost on a stage-B server. Playwright needs no fallback: stdout, stderr and
  steps are already part of the final result.

## 5. Attachments

```
POST /api/v1/projects/{key}/launches/{id}/attachments
Content-Type: image/png
X-FastProof-Attachment-Name: screenshot.png
<raw bytes, streamed from disk>
```

Response `201 {id, sha256, size}`. Then the attachment is referenced by `id` in the attempt's final result.

- Upload **after the attempt**, in the background, before its final result (the server rejects unknown ids),
  at most 4 uploads at a time per process, files streamed from disk, never read into memory as a whole.
- **Dedup**: the reporter hashes the content first (sha256) and uploads each hash once per launch; later
  references reuse the id.
- Header values are printable ASCII; other names are percent-encoded in the header, and the display name is
  sent in the result reference (`name`).
- Text attachments (`text/*`, JSON) up to 4 MiB are masked before hashing and upload.
- Playwright: every `result.attachments` entry (screenshots, video, trace zip, `testInfo.attach`); names
  without an extension get the file's extension (`trace.zip`, so the server recognises traces).
  pytest: `pytest_fastproof.attach(body, name, content_type)` and `attach_file(path)`.
- `400`/`413`/`415` or an unreadable file: the attachment is skipped with a warning; network errors and `5xx`:
  the attempt goes to the spool with its files.

## 5a. Direct uploads

A server with an S3 store can take attachments straight into the bucket through pre-signed URLs. The
Playwright reporter, pytest-fastproof and `fastproof upload <dir>` do it for attachments of at least
`FASTPROOF_DIRECT_UPLOAD_MIN_BYTES` (default 1 MiB) unless `FASTPROOF_DIRECT_UPLOAD_MODE=off`. Other reporters
may implement it; the server path of section 5 keeps working everywhere.

```
POST /api/v1/projects/{key}/launches/{id}/attachments/direct
{"items": [{"sha256": "<hex>", "size": 5242880, "contentType": "video/webm", "name": "video.webm"}]}

200 {"items": [{"sha256": "...", "status": "upload", "uploadId": "<uuid>", "method": "PUT", "url": "https://...",
                "headers": {"content-type": "application/octet-stream", "x-amz-checksum-sha256": "<base64>"},
                "expiresAt": "..."}]}
```

1. Hash the file (after masking, for text attachments), then ask with 1 to 100 items. Answers come in request
   order: `exists` (use `id` at once), `upload`, or `refused` (`code`, `limit`: use section 5 for that file).
2. `PUT` the bytes to `url` with exactly `headers` plus `Content-Length`; send **no** `Authorization` header and
   never log the URL (it is a credential until `expiresAt`). Stream from disk.
3. `POST .../attachments/direct/{uploadId}/complete` (no body): `201 {id, sha256, size}`, or `200` with the same
   body when it was completed before. Reference `id` in the result as usual.

Fallbacks, all silent except one warning per run:

- `404`, `405` or `501` on the first call: the server has no direct uploads; use section 5 for the rest of the
  run.
- The PUT gets no answer (DNS, connection, TLS, timeout): the bucket is not reachable from this runner; use
  section 5 for this file and the rest of the run.
- The PUT answers an error, the completion answers `410` or `422`, or the item is `refused`: use section 5 for
  this file.
- `409 not_uploaded` or `409 verification_in_progress`: retry the completion a few times with backoff; `5xx`
  and network errors of the FastProof calls are handled like those of section 5 (retries, then the spool).

The spool format does not change: spooled attachments are sent by the flush like any other, directly when the
flushing tool supports it.

## 6. Retries, backoff and the circuit breaker

- Retryable: no response, `408`, `429`, `5xx`. Backoff with full jitter: `min(8 s, 250 ms × 2^n)`, between half
  and the full value; `Retry-After` is honoured up to 60 s.
- During the run the background sender does not wait inside a request: a failed batch goes back to the head of
  the queue and is retried on the next tick. Uploads and launch creation retry 1–2 times with backoff.
- Five consecutive failures, or `401`/`403`/`404`, open the breaker: the reporter stops calling the server for
  the rest of the run and writes everything to the spool (one warning). Other `4xx` are warned about once and
  dropped; they would fail again.
- End of the run: wait for uploads and the queue up to the flush timeout (30 s); spool what is left; if the
  spool has data and the server answers, send it right away within the same deadline; finish the launch when
  asked; print one summary line, plus the command to send the spool later.
- Reporting errors never change the exit code and are never raised into a test.

## 7. Offline spool (format v1)

```
<spool>/<session>/meta.json        {"v":1, "reporter":"pytest/0.1.0", "project":"shop", "launch":{LaunchStart},
                                    "createdAt":"...", "pid":1234, "host":"ci-runner-3", "ended":true, "finish":"finished"}
<spool>/<session>/results.ndjson   {"v":1, "result":{ReportResult}, "blobs":[{"sha256","name","contentType","size"}]}
<spool>/<session>/blobs/<sha256>   attachment bytes (already masked)
<spool>/<session>/progress.json    {"lines": 120}   lines already sent
<spool>/.staging/<runId>/<sha256>  pytest only: bodies of attach() calls until they are uploaded
```

- `<session>` is `<UTC yyyymmddThhmmss>-<pid>-<random>`; one per reporter process.
- In `results.ndjson`, attachments not yet on the server are referenced as `{"id": "blob:<sha256>"}`; ids
  already uploaded are kept as they are.
- Lines are appended and fsynced one by one; files are written to a temporary name and renamed.
- **Budget**: the whole spool directory is limited (default 200 MB). Attachments of passed and skipped tests may
  use only half of it, so failures keep room for screenshots and traces; over the limit, attachments are dropped
  first, then results (counted and reported at the end).
- `meta.json` holds no token and no URL; the sender uses its own configuration.
- **Sending**: a session can be sent when it has `ended` or its process is gone (same host, dead pid). For each
  session: `POST launches` with the stored `LaunchStart` (idempotent by external id), upload `blobs/` once per
  hash, replace `blob:` ids, post results in batches of 200 (idempotent by client id), update `progress.json`
  after each batch, finish the launch if `finish` is set, delete the session. Interrupted sends resume.
- Who sends: the next run of either reporter (in the background, same project), the end of the same run when
  the server is back, `npx fastproof-playwright flush [--spool DIR]` or `python -m pytest_fastproof flush
  [--spool DIR]`. Both read the same format, so either tool can send any session. The `flush` commands need
  `FASTPROOF_URL` and a token; each session goes to the project in its `meta.json`, and `FASTPROOF_PROJECT`
  limits a flush to one project.

## 8. Trace context per attempt

- Every attempt gets a new W3C trace id; `traceparent: 00-<trace id>-<span id>-01`, and
  `baggage: fastproof.launch=<external id>,fastproof.test=<test id>,fastproof.attempt=<n>` (values
  percent-encoded). The final result carries `traceparent`; the server stores its trace id on the attempt, so
  FastMock and tracing backends can be correlated with it.
- Playwright: the reporter (runner process) puts a random seed into the workers' environment; the reporter and
  the `fastproofTrace` fixture derive the same ids from `sha256(seed, test id, retry)`. The fixture also writes
  the `traceparent` it used to the `fastproof.traceparent` annotation, which wins. `headers({newSpan: true})`
  gives a new span id per request. Propagation: `fastproofPropagate: 'all'` adds the headers to
  `extraHTTPHeaders`; a list of origins adds them only to browser requests to those origins (`context.route`);
  `traceHeaders(testInfo)` for anything else.
- pytest: the test process creates the context at `pytest_runtest_logstart`; fixture `fastproof_trace`,
  `pytest_fastproof.trace()`, `.headers(new_span=False)`, `.env()` (a copy of the environment with
  `TRACEPARENT` and `BAGGAGE` for child processes, following OpenTelemetry environment carriers).

## 9. Secret masking at the source

Before anything is queued, spooled or uploaded, values are replaced with `****`:

- values of environment variables whose names match `FASTPROOF_TOKEN`, `*TOKEN*`, `*SECRET*`, `*PASSWORD*`,
  `*PASSWD*`, `*_KEY`, `*APIKEY*`, `*API_KEY*`, `*CREDENTIAL*` plus configured names (their URL-encoded form
  too); values shorter than 4 characters, booleans and short numbers are ignored;
- configured literal values and regular expressions;
- applied to test and step names, full names, parameters, labels from annotations, error messages and traces,
  stdout/stderr, log lines, attachment names and text attachment contents.

Masked parameter values collapse to `****`; give such cases distinct non-secret parameters if they must stay
separate test cases.

## 10. Test plans

Allure format `{"version": "1.0", "tests": [{"id": "...", "selector": "..."}]}` from `FASTPROOF_TESTPLAN`,
`ALLURE_TESTPLAN_PATH` or the reporter option.

- Playwright selectors: `file › describe › title` (the FastProof full name), `file#describe title` (Allure),
  `file:line[:column]`; ids from annotations `fastproof.id`, `allure_id`, `as_id`. `testPlanGrep()` builds a
  `grep` for `playwright.config` (title selectors); the `fastproofTestPlan` auto fixture of
  `@franshub/fastproof-playwright/fixture` skips tests that are not in the plan (all forms, ids included).
- pytest selectors: node id with or without parameters, allure-pytest full name (`package.module.Class#test`);
  ids from `@pytest.mark.fastproof_id("…")` or `allure_label(..., label_type="as_id")`. Tests not in the plan
  are deselected (`pytest_deselected`). An unreadable plan is ignored with a warning (fail-open).

## 11. Writing a new reporter

1. Map the framework's events to: test begins (running result), output and steps (log lines), attempt ends
   (final result + files). Hooks only enqueue; one background sender per process does the HTTP.
2. Pick a client id scheme that is unique per run and attempt and reproducible in every process that needs it.
3. Reuse the spool format above byte for byte, so `flush` from any package sends it.
4. Test against a fake server for the live path (running results and logs accepted) and against the real
   server for the stage-B path (both rejected), with the server down, and with parallel workers.
